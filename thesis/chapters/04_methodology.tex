\section{Methodology}
\label{sec:methodology}

\subsection{Benchmarks}

The experiments use three benchmarks that differ in answer length and constraint structure.

\textbf{GSM8K} is a grade-school mathematics benchmark with numeric final answers.

\textbf{Countdown-cd4} is a constrained arithmetic planning task. Each problem provides four numbers and a target, and the model must construct a valid sequence of arithmetic operations that reaches the target.

\textbf{Trip Planning} is a structured natural-language planning benchmark. The model must generate an itinerary with ordered city visits and exact stay durations. Unlike Countdown, the output is longer and written in natural language.

Together, these benchmarks span a progression from numeric reasoning (GSM8K), to symbolic planning (Countdown), to structured natural-language planning (Trip Planning).

\subsection{Models and Prompt Modes}

The evaluation compares two masked diffusion language model families, \textbf{LLaDA} and \textbf{Dream}, with two autoregressive families, \textbf{Qwen2.5} and \textbf{Llama~3.1}. Each family is evaluated at approximately 7B--8B parameter scale, using both base and instruction-tuned variants where available.

Prompt format is treated as an experimental variable because instruction-tuned models are typically trained with chat-style templates, while many reasoning benchmarks are written as flat completion prompts. Three prompt modes are used:

\begin{itemize}
    \item \textbf{\texttt{base\_native}}: Used for base models. The benchmark is presented in its original completion format.
    \item \textbf{\texttt{instruct\_templated}}: The task is wrapped in the model's chat template. This is the native chat setting for instruction-tuned models.
    \item \textbf{\texttt{instruct\_flat}}: The same flat benchmark text is given to an instruction-tuned model without a chat wrapper. This serves as a diagnostic for prompt-interface sensitivity.
\end{itemize}

The flat and templated instruct settings are not interchangeable: one follows the chat format expected by instruction tuning, while the other keeps the benchmark in the completion-style format used for base models. The prompt-sensitivity results in Section~\ref{sec:results-gsm8k} and Figure~\ref{fig:gsm8k-prompt} quantify the effect of this choice.

\subsection{Unified Evaluation Pipeline}
\label{sec:unified-evaluation-pipeline}

All models are evaluated through the same measurement pipeline after generation. A benchmark instance and prompt mode first define the input. The model then produces completions through its own inference mechanism: autoregressive models decode left to right, while diffusion models use iterative masked-token refinement. The resulting completions are passed to the same task-specific parsers and aggregate metrics. This design keeps the generation mechanism separate from the scoring procedure.

\subsection{Generation and pass@k Evaluation}

Figure~\ref{fig:eval-pipeline-ar-vs-dllm} shows the split between generation
and scoring. Diffusion runs are generated with \texttt{fast-dLLM}; AR runs are
generated with \texttt{vLLM}. After generation, the same downstream parsers and
metrics are used for both groups. Deterministic runs use temperature $=0$ and
one completion per question. Stochastic runs use temperature $=0.7$.

The term pass@1 needs a little care. I use \emph{greedy $n=1$ accuracy} for
the deterministic temperature-$0$ run with one completion. \emph{First
stochastic sample accuracy} means the correctness of the first saved completion
from a stochastic run. \emph{Estimated stochastic pass@1} is different again:
it is the $k=1$ case of the pass@k estimator, so for a question with $r$ correct
samples among $n$ saved samples, it equals $r/n$. Unless a result is explicitly
called deterministic or first-sample accuracy, pass@1 in stochastic pass@k
tables and figures refers to this estimated stochastic pass@1.

The sample budget is benchmark-dependent. GSM8K and Countdown-cd4 use up to
$128$ samples per question. Trip Planning uses up to $64$ samples because the
outputs are longer and the parser is stricter.

For a question with $n$ generated samples and $r$ correct samples, the pass@k
estimator is:

\begin{equation}
    \operatorname{pass@}k = 1 - \frac{\binom{n-r}{k}}{\binom{n}{k}}.
\end{equation}

This estimates the probability that at least one of $k$ sampled outputs is
correct. Greedy accuracy asks what happens when the model gets one deterministic
try. Stochastic pass@k asks whether the saved candidate set contains a correct
solution. The distinction is central here because large-$k$ reasoning
evaluations show that first-sample quality and candidate-set coverage can lead
to different model rankings \cite{yue2025rlvr}. Throughout the thesis, pass@k
is treated as coverage in the sampled completions. It is not a claim that a
deployed system could identify the correct candidate without a verifier.

\subsection{Parser-Controlled Scoring}
\label{sec:parser-details}
\label{sec:methodology-parsers}

Raw completions are not scored by string matching alone. Each benchmark has a parser that extracts the relevant answer structure and checks task-specific validity. A sample can fail because the parser cannot read the output, because the answer is not in the required format, or because the parsed answer violates the task constraints:
\begin{itemize}
    \item \textbf{Parse failure}: the output cannot be interpreted structurally
    \item \textbf{Format failure}: the answer is present but not in the required format
    \item \textbf{Validity failure}: the structured output violates task constraints
\end{itemize}

Only parsed and validated outputs are converted into correctness labels.

\textbf{GSM8K.} Gold answers are extracted from the official final-answer
marker in the dataset. Model outputs are scored with a strict boxed-answer
extractor, requiring the final numeric answer to appear in
\texttt{\detokenize{\boxed{...}}} or \texttt{\detokenize{\fbox{...}}}.
Numeric formatting is normalized when possible, and predictions are compared
with the gold value within a small tolerance. A more permissive final-number
scorer is reported only for parser-sensitivity analysis and does not replace
the primary strict scores. Because it uses a different extraction rule, it can
raise or lower measured accuracy.

\textbf{Countdown-cd4.} The scorer expects a leading chain of comma-separated binary equations (e.g., \texttt{a+b=c,c-d=e}). The chain must evaluate to the target, use only the provided numbers, respect usage constraints, and introduce intermediate values only through earlier steps. Allowed operations are addition, subtraction, multiplication, and division. Invalid syntax, incorrect evaluation, or improper number usage result in failure.

\textbf{Trip Planning.} The scorer parses generated itineraries to extract total duration, city visit ranges, and flight transitions. From this information, it reconstructs the ordered sequence of cities and their durations, which are then compared against the required plan. Errors such as malformed structure, missing components, incorrect ordering, or duration mismatches lead to failure.

\subsection{Per-Question Accuracy Analysis}

Aggregate metrics such as pass@k summarize overall performance, but they do not reveal whether different models succeed on the same questions. For each question and model, the analysis records the fraction of generated samples that are correct.

Pearson correlation between these per-question vectors measures behavioral alignment. High correlation means that two models tend to succeed and fail on similar instances; lower correlation indicates more complementary behavior.

The same representation enables an \textbf{oracle union analysis}. This analysis counts a question as solved if any model in a set produced a correct sample. It is not a deployable method, because it assumes access to correctness at selection time, but it shows how much complementarity exists in the sampled outputs.

\subsection{Evaluation Conditions}

Models within each benchmark comparison share the same downstream dataset
subset, prompt mode, parser, temperature, and sample budget where applicable.
The inference backend remains model-specific.

\begin{itemize}
    \item GSM8K: 128 questions, 128 samples (main); 256 questions, 16 samples (few-shot ablation)
    \item Countdown-cd4: 992 questions, 8 few-shot examples, 128 samples
    \item Trip Planning: 200 questions, 2 few-shot examples, 64 samples
\end{itemize}

Generation length is adjusted per task: shorter for Countdown expressions and longer for GSM8K reasoning traces and Trip Planning outputs. Dataset subsampling uses fixed seeds where implemented in the loaders, but repeated sampling seeds are not available as independent runs. Command-level configuration details are left to the repository artifacts rather than repeated as a separate table.
